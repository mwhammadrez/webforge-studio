Dependency direction:
- `renderer` may communicate only with `preload`.
- `preload` may communicate only with allowlisted `main` IPC handlers.
- `main` uses `core` services.
- `core` services may use `shared`, SQLite, filesystem, and plugin runtime.
- `renderer` must never access Node.js APIs, filesystem, child processes, secrets, or arbitrary URLs directly.

Technology table:
| Layer | Choice | Version | Reason | Alternative rejected |
|---|---|---|---|---|
| Desktop shell | Electron | [verify in Phase 0] | Chromium-based preview, mature file/process APIs, strong Windows support | Tauri, because Rust and OS WebView differences add risk for browser automation and local tool execution |
| UI | React + TypeScript | [verify in Phase 0] | Mature component ecosystem and strong typing | Plain HTML/JS, because it lacks maintainable typed structure |
| State | Zustand or React Query | [verify in Phase 0] | Simple typed local state and async server-state handling | Redux, because it adds boilerplate without a clear benefit here |
| Styling | Tailwind CSS | [verify in Phase 0] | Fast consistent theming and RTL support through logical properties | Custom CSS only, because theme consistency becomes harder |
| Database | SQLite | [verify in Phase 0] | Local, zero-server, reliable persistence | PostgreSQL, because this is a single-user desktop app |
| Validation | Zod | [verify in Phase 0] | Shared runtime and TypeScript validation at IPC and plugin boundaries | Manual validation, because it is error-prone |
| Testing | Vitest + Playwright | [verify in Phase 0] | Fast unit tests and real Electron end-to-end verification | Jest only, because Electron E2E needs a browser-level runner |
| HTTP | Node.js built-in fetch or a vetted HTTP client | [verify in Phase 0] | Fewer dependencies and explicit timeout control | Multiple HTTP libraries |
| AI | DeepSeek API | [verify in Phase 0] | User requested DeepSeek integration | Other providers unless the user changes settings |

Core modules:
- `ProjectService`: creates, opens, renames, validates, indexes, and deletes local website projects.
- `ExtractionService`: downloads and normalizes a public website into a local project.
- `PreviewService`: starts, stops, and monitors a local static or framework-aware preview server.
- `VisualEditorService`: maps preview selections to source files and applies reversible edits.
- `PluginService`: discovers, validates, configures, executes, and records plugins.
- `AIBuilderService`: turns a brief into a project plan, files, and a generated website.
- `ToolDiscoveryService`: searches and evaluates GitHub tools, but never installs or runs one without approval.
- `SettingsService`: manages theme, language, paths, ports, AI provider, and encrypted credentials.
- `LoggingService`: writes structured local logs with correlation IDs and redaction.

Cross-cutting design:
- All IPC inputs are validated with Zod schemas before use.
- Every filesystem write occurs inside the active project directory or an explicitly user-selected directory.
- Every network call has a timeout, cancellation support, retry only for idempotent requests, exponential backoff with jitter, and a maximum retry count.
- Every long-running operation has progress events, cancellation, and a final success, failure, or partial-failure state.
- No empty catch blocks. Errors are typed, contextual, logged once at the boundary, and shown in Persian in the UI.
- Every generated or extracted project receives a unique ID, creation timestamp, source URL when applicable, and integrity manifest.
- Unsafe operations that overwrite files create a timestamped backup first.
- SQLite migrations are versioned, forward-only in normal operation, and tested before release.
- Application shutdown stops preview servers, terminates child processes, closes database connections, and flushes logs.

Key data flows:

Extraction:
1. User enters a URL in the Extract screen.
2. UI validates the URL and sends it over typed IPC.
3. Main process validates the URL, blocks private network addresses, creates a project record, and starts extraction.
4. Extraction downloads HTML, CSS, JavaScript, images, fonts, and referenced assets within configured limits.
5. The service rewrites local asset paths, records a manifest, and saves files under the project folder.
6. Progress, warnings, skipped resources, and final statistics stream to the UI.
7. User can open the resulting project in Preview.

Visual editing:
1. User opens a local project and starts Preview.
2. The embedded preview loads the local site.
3. User activates Select mode and clicks an element.
4. The editor identifies the element, its tag, text, attributes, computed styles, image source, and nearest source mapping.
5. The side panel shows editable Persian fields for the selected element type.
6. User edits values; the editor creates a reversible change proposal.
7. On Save, the service updates the correct source file, creates a backup, records the change, and refreshes the preview.
8. Undo and redo operate on the recorded change history.

Plugin execution:
1. User opens Plugins and adds a tool.
2. User provides a manifest or lets the app analyze the supplied script and propose a manifest.
3. The app validates the manifest, input schema, command, working directory, output contract, and security constraints.
4. User fills the generated Persian form.
5. Plugin runtime executes the tool as a child process with timeout, cancellation, environment allowlist, and streamed logs.
6. Output files are copied or linked into the selected project location.
7. The run history stores command metadata, duration, exit code, logs, and produced files.

AI website generation:
1. User opens AI Builder and writes a website brief in Persian or English.
2. User selects page type, pages, color preference, language, sections, and output folder.
3. The app validates input and calls DeepSeek only after showing the estimated action and receiving user approval.
4. The service produces a structured project plan, then generates files incrementally.
5. Generated files are validated, formatted, and written to a new project folder.
6. The app opens the generated project in Preview.
7. User can edit the result with the Visual Editor or run plugins on it.

## Functional requirements

### Application shell

- FR-1: WHEN the user launches WebForge Studio THE SYSTEM SHALL display a Persian RTL dashboard within 5 seconds on a normal development machine.
- FR-2: WHEN the user opens Settings THE SYSTEM SHALL allow switching between Dark and Light themes and persist the choice.
- FR-3: WHEN the user changes theme THE SYSTEM SHALL apply the selected theme immediately without restarting the application.
- FR-4: WHEN the application starts THE SYSTEM SHALL restore the last selected theme, window size, and last opened project.
- FR-5: WHEN any main screen is opened THE SYSTEM SHALL display Persian labels, Persian validation messages, and RTL layout.
- FR-6: WHEN mixed Latin content such as a URL, file path, code, or email appears THE SYSTEM SHALL isolate it with correct bidirectional handling so it remains readable.
- FR-7: WHEN the user opens Settings THE SYSTEM SHALL allow configuring default projects directory, preview port range, AI provider settings, extraction limits, and plugin directory.
- FR-8: WHEN a required setting is missing or invalid THE SYSTEM SHALL show a specific Persian error and prevent the related operation from starting.

### Project management

- FR-9: WHEN the user clicks New Project THE SYSTEM SHALL allow selecting or creating a local folder.
- FR-10: WHEN the user opens a project folder THE SYSTEM SHALL detect HTML entry files, package metadata, framework hints, asset folders, and whether the project is static or requires a build step.
- FR-11: WHEN the selected folder does not contain a recognizable website entry point THE SYSTEM SHALL show a Persian explanation and list detected files instead of failing silently.
- FR-12: WHEN the user deletes a project THE SYSTEM SHALL require explicit confirmation showing the exact folder path and move it to a timestamped backup location before removal from the project list.
- FR-13: WHEN the user renames a project THE SYSTEM SHALL update the project record without moving or rewriting project files unless the user explicitly approves a folder rename.
- FR-14: WHEN the user opens Projects THE SYSTEM SHALL show project name, path, type, last opened date, file count, and last preview status.

### Website extraction

- FR-15: WHEN the user enters a valid public HTTP or HTTPS URL and clicks Extract THE SYSTEM SHALL create a new local project and begin extraction.
- FR-16: WHEN extraction starts THE SYSTEM SHALL display progress including current resource, completed count, total discovered count, downloaded bytes, and elapsed time.
- FR-17: WHEN extraction completes THE SYSTEM SHALL save HTML, CSS, JavaScript, images, fonts, and directly referenced local assets into the project folder.
- FR-18: WHEN extraction completes THE SYSTEM SHALL rewrite relative asset references so the extracted site can open from the local project folder.
- FR-19: WHEN extraction encounters a resource that cannot be downloaded THE SYSTEM SHALL record it as a warning, continue processing other resources, and display the failed URL and reason in the extraction report.
- FR-20: WHEN extraction exceeds the configured maximum file count, maximum total size, maximum depth, or time limit THE SYSTEM SHALL stop safely, preserve downloaded files, and show a partial-success report.
- FR-21: WHEN the user cancels extraction THE SYSTEM SHALL stop new downloads, preserve completed files, terminate active requests, and mark the project as partially extracted.
- FR-22: WHEN the user enters a private, loopback, link-local, or otherwise non-public URL THE SYSTEM SHALL reject it with a Persian security message.
- FR-23: WHEN extraction completes THE SYSTEM SHALL generate `webforge.manifest.json` containing source URL, extraction time, file list, hashes, warnings, and skipped resources.
- FR-24: WHEN the extracted site contains JavaScript-rendered content THE SYSTEM SHALL offer a rendered-DOM extraction mode using an embedded browser and clearly label the resulting files as rendered output.

### Preview and local running

- FR-25: WHEN the user opens a static project and clicks Preview THE SYSTEM SHALL start a local HTTP server on an available configured port and load it in the embedded preview.
- FR-26: WHEN the user opens a project containing `package.json` and a recognized dev or preview script THE SYSTEM SHALL show the detected command and require explicit approval before executing it.
- FR-27: WHEN a preview server starts THE SYSTEM SHALL display its URL, port, process ID, status, and a Stop button.
- FR-28: WHEN the user clicks Stop Preview THE SYSTEM SHALL terminate the server process and release the port.

## State machines

### Project

States: `ready`, `extracting`, `partial`, `error`, `archived`.

| From | To | Guard | Forbidden transition and error |
|---|---|---|---|
| `ready` | `extracting` | No active extraction for the project | `error`: `PROJECT_ALREADY_EXTRACTING` |
| `extracting` | `ready` | Extraction completed without blocking errors | None |
| `extracting` | `partial` | User cancelled or a configured limit stopped extraction | None |
| `extracting` | `error` | Fatal extraction failure | None |
| `partial` | `extracting` | User retries extraction | None |
| `error` | `extracting` | User retries after reviewing the error | None |

## Plugin manifest contract

Each user-supplied tool must provide `plugin.manifest.json`:

```json
{
  "name": "example-tool",
  "displayName": "نام فارسی ابزار",
  "version": "1.0.0",
  "runtime": "node",
  "command": "node",
  "args": ["tool.js"],
  "cwd": ".",
  "inputs": [
    {
      "key": "siteUrl",
      "label": "آدرس سایت",
      "type": "url",
      "required": true
    },
    {
      "key": "outputFolder",
      "label": "پوشه خروجی",
      "type": "projectPath",
      "required": true
    }
  ],
  "outputs": [
    {
      "key": "report",
      "type": "file",
      "path": "report.json"
    }
  ],
  "permissions": {
    "network": false,
    "projectWrite": true,
    "environment": []
  },
  "timeoutSeconds": 300
}
```

The application must:
- Validate this schema with Zod.
- Generate the Persian input form automatically.
- Pass inputs as documented by the plugin, using arguments, stdin, or environment variables according to the manifest.
- Capture stdout, stderr, exit code, duration, and output files.
- Reject plugins that declare no command, unsafe paths, or permissions the user did not approve.

## Internationalization

- Primary locale: `fa-IR`.
- Direction: `dir="rtl"` and `lang="fa"` on the root document.
- All user-facing strings live in `src/shared/i18n/fa.json` with stable English keys.
- Use CSS logical properties: `margin-inline-start`, `padding-inline-end`, `inset-inline-start`, and equivalent properties.
- Use `Intl.DateTimeFormat`, `Intl.NumberFormat`, and `Intl.PluralRules` with `fa-IR`.
- Store all timestamps as UTC ISO-8601.
- Display dates using the Persian calendar through `Intl` with the `persian` calendar.
- Use Persian digits in user-facing counters, dates, and statistics.
- Keep Latin digits in code, file paths, URLs, ports, and technical logs.
- Normalize Arabic yeh (`ي`) and kaf (`ك`) to Persian yeh (`ی`) and kaf (`ک`) in user search input while preserving the original text where needed.
- Preserve zero-width non-joiner (`U+200C`) in Persian text.
- Use bidirectional isolation for URLs, paths, emails, and code snippets.
- Use a Persian font stack with verified Persian glyph coverage and appropriate Latin fallbacks. [verify in Phase 0]
- Ensure RTL-correct icons, navigation, progress bars, tooltips, context menus, and print output.

## Non-functional requirements

### Security

- NFR-1: All IPC messages must be validated with Zod at the main-process boundary.
- NFR-2: The renderer must have `contextIsolation: true`, `nodeIntegration: false`, and a narrowly scoped `contextBridge` API.
- NFR-3: The app must block extraction requests to private, loopback, link-local, and multicast IP ranges.
- NFR-4: All SQL access must use parameterized queries.
- NFR-5: All file writes must be confined to approved project roots.
- NFR-6: All downloaded files must receive randomized or sanitized names and must never be executed automatically.
- NFR-7: The app must enforce maximum extraction size, file count, depth, and duration.
- NFR-8: The app must enforce maximum uploaded or selected image size and validate image type by content, not only extension.
- NFR-9: All secrets must be stored encrypted at rest and excluded from logs, IPC payloads, screenshots, and error messages.
- NFR-10: All logs must redact API keys, tokens, passwords, cookies, authorization headers, and personal data.
- NFR-11: Every plugin execution must use an explicit timeout, working-directory restriction, environment allowlist, and cancellation support.
- NFR-12: Every plugin permission request must be explicit and approved by the user.
- NFR-13: The app must not execute downloaded website JavaScript with elevated filesystem or process privileges.
- NFR-14: The app must use a Content Security Policy that prevents remote script injection into the application UI.
- NFR-15: Dependency audit must run in the verification gate and fail on known high-severity vulnerabilities. [verify in Phase 0]

- NFR-16: Every network request must have a timeout of 30 seconds unless the user configures a different value.
- NFR-17: Every child process must have a configurable timeout and a hard maximum of 30 minutes.
- NFR-18: Retries are allowed only for idempotent GET requests and must use exponential backoff with jitter, maximum 3 attempts.
- NFR-19: A crash of one preview server or plugin must not crash the application.
- NFR-20: Application shutdown must terminate child processes and release ports.
- NFR-21: Every file overwrite must create a timestamped backup.
- NFR-22: Every failed operation must leave the previous valid state intact.

- NFR-28: The application must handle projects with up to 20,000 files without freezing the UI.
